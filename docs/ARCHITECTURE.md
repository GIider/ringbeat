# Architecture

Vanilla ES modules, no build. `npm start` serves the folder (`scripts/serve.mjs`; `npm run dev` adds live reload), `npm test` runs the node tests, `npm run smoke` the headless UI test.

```
index.html / style.css        the phone (#phone: SVG shell, #lcd with every screen as <section class="screen">, key hit
                              areas), and canvas #stage (the 8-bit highway, inside the #nowplaying screen of the LCD)
assets/           phone.svg, icon.svg, fonts/rb-pixel{,-bold}.ttf (generated by `npm run font`)
src/
  rtttl.js        parser: text -> { name, bpm, notes[], warnings[] }
  bot.js          headless bot players (skill ladder + weakness specialists) running the real Game; measureChart() -> rating/tags
  listview.js     pure song-list sort/filter (default, difficulty, title, BPM; all / unplayed / no FC)
  difficulty.json generated by `npm run bench` (scripts/bench.mjs); loaded at startup, falls back to density stars
  chart.js        song -> chart (difficulty filter, lane assignment, holds, short holds, doubles); filtered-out notes become auto-played `backing`
  practice.js     sliceChart / scaleChart: pure chart transforms for training
  songs.js        built-in song data (id, category, title, tag, rtttl) + CATEGORIES
  library.js      derived metadata (BPM, length, stars, note counts), custom entries, hashing
  mysongs.js      saved custom songs (CRUD, import/export, injectable storage)
  composer.js     Nokia-style note editor state; toRTTTL / fromRTTTL
  scores.js       highscores store (injectable storage)
  settings.js     persisted settings incl. controller bindings and training options
  game.js         judging, scoring, holds, FC/AP, pause/restart; audio-clock only
  input.js        keyboard + pointer -> lane events with audio-clock timestamps
  gamepad.js      Gamepad API poller, default bindings, lane folding
  nav.js          spatial focus navigation shared by keyboard and gamepad
  render.js       8-bit canvas highway inside the LCD, score/accuracy/combo rows, effects (visual only, never used for judging)
  pixelfont.js    5x7 glyph table for the LCD font (scripts/build-font.mjs -> TrueType)
  pixelart.js     1-bit sprites + SVG data-URI / CSS-mask helpers
  cover.js        procedural 72x28 picture-message art per song
  perf.js         frame/section profiler (ring buffers, percentiles); no-op until enabled
  perfhud.js      corner overlay + report copy for perf.js
  synth.js        Web Audio voices (piezo buzzer, smooth), ticks, miss thud, key click, power-on jingle
  calibration.js  latency calibration
  share.js        #s=<base64url> share links
  main.js         state machine, screen wiring, phone layout/modes + soft keys, play/results flow
scripts/serve.mjs   dependency-free dev server (LAN URLs, no-store)
scripts/perf-bench.mjs  speed micro-benchmarks incl. headless render, whole-song frame replays, alloc per call (`npm run perf`)
scripts/perf-play.mjs   plays songs in headless Chromium with a key bot and reports frame pacing (`npm run perf:play`)
tests/
  core.test.mjs   node tests: library, scores, practice transforms, game FC/AP, bindings
  rtttl.test.html parser/chart tests in the browser (title shows PASS/FAIL)
  smoke.html      UI smoke test driving index.html in an iframe
```

## Key decisions

- **One persistent phone.** The phone never moves: menus, play, pause and results are all screens in the same LCD
  (`body[data-mode]` is `menu`/`play`/`pause` for styling only). The `#nowplaying` screen is the `#stage` canvas, drawn at
  one canvas pixel per LCD pixel (`renderer.setPixelScale(--u)`), two colours (LCD ink on the green backlight), scaled up
  with `image-rendering: pixelated`. Narrow screens drop the shell: the LCD fills the viewport.
- **Crisp pixel text.** The LCD font size is 20 or 30 px (2 or 3 px per font pixel), chosen from the LCD width, never
  a fractional scale; canvas text uses multiples of 10 px.
- **Soft keys.** Each screen declares `data-title`, `data-soft-left`, `data-soft-right`. Right soft key = `back()`;
  left = a per-state action (`softLeft`), defaulting to "select the focused item". Phone keypad 2/4/6/8/5 map to
  the same navigation as arrows/d-pad.

- **Training = chart transform.** Speed and loop are applied to the generated chart before `Game.start`, so
  `Game` needs no special cases. `sliceChart` also shifts the beat-grid origin so the backing pulse stays aligned.
- **Focus navigation, not custom menus.** Every screen is ordinary focusable DOM; keyboard arrows and gamepad
  d-pad both go through `nav.js` (nearest control in direction), which keeps touch/mouse/keyboard/pad consistent.
- **Selection by focus.** In the song list, focusing a row selects it; confirm on the selected row plays.
  A mouse click only selects (double-click plays) so pointer users don't launch songs by accident.
- **Pad time.** Pad edges carry `performance.now()`-domain timestamps and go through the same `eventAudioTime` as keys.
- **Persistence.** `ringbeat.v1` (settings) and `ringbeat.scores.v1` (scores); all reads are guarded and validated, so
  blocked or corrupted storage falls back to defaults.

## Profiling

- **In the browser:** open with `?perf` (or press F3 during play) for the overlay: FPS, frame p50/p95/max, and mean ms for
  `pad`, `update`, `draw`, `chartgen`, `library`. F4 prints a table and copies the JSON report. `__ringbeat.perf.report()`
  gives the same data from devtools. Disabled, the hooks are single-boolean no-ops.
- **In node:** `npm run perf` runs the micro-benchmarks. `-- --filter chart` selects cases, `--json f.json` saves results,
  `--baseline f.json` adds a Δ% column, `--fail-over 25` exits nonzero on a regression. Timings are machine-specific, so
  record a baseline on the same machine first. `canvas calls/frame` for `render.draw` is deterministic and a good
  regression signal.
  Columns include p99/max (stutter is about the worst frame) and, because `npm run perf` runs with `--expose-gc`,
  `alloc B/call` (approximate heap growth per call; steady-state `render.draw` should stay near zero). `frames.*` cases
  replay a whole song at 60 Hz and report per-frame percentiles; `--fail-over-max N` also gates the worst-frame delta.
- **In a real browser:** `npm run perf:play [-- --songs 0,6,12 --diff hard --seconds 30]` plays songs with a keyboard bot
  and prints fps, long-frame %, frame p50/p95/p99/max and draw/update p99. The HUD also counts main-thread long tasks.
